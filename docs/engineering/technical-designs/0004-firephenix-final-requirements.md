## 1. 产品目标与边界

基于现有 Thunderbird Android 项目开发可日常使用的个人邮件客户端，优先满足个人 Outlook、同账户多别名、翻译、总结及荣耀手机体验。保留收发、多账户、附件、搜索、文件夹、草稿和通知等上游成熟能力，减少核心代码侵入，便于同步上游，保留开源许可证和原作者署名。

- 应用品牌：英文 FirePhenix，中文 火凤凰，采用用户指定的 Phenix 拼写。
- 正式应用标识沿用 app.firephenix.android；调试版本沿用 app.firephenix.android.debug。
- 当前开发平台为 Android，开发电脑为 M1 MacBook Air，目标真机为荣耀 500 Pro。
- Outlook 邮件使用原生邮件客户端能力；OAuth 登录可以跳转浏览器。
- 日历、联系人和相关 Microsoft 365 功能允许通过外部浏览器链接解决；本阶段不承诺完整双向同步。
- 不开发桌面版或 iOS。以后桌面源码能共享时不按 macOS、Windows、Linux 重复拆分。
- 当前不部署自建 Push Gateway，不提前实现未来服务器。复用上游同步、后台收信和通知，FCM／荣耀 Push 只保留扩展接入能力，不能把 SDK 或接口预留写成真实实时邮件推送。

## 2. 品牌文字与图标

### 2.1 界面文字

- 本 App 所有界面中表示自身品牌的 Thunderbird 及其本地化名称，改为 FirePhenix。
- 现有中文（含简体、繁体）、日文和韩文资源中的自身品牌均使用“火凤凰”；其他语言使用 FirePhenix。
- 覆盖首次使用、账户导入、邮件页面、设置、关于、对话框、通知及无障碍描述等自身品牌位置。
- 桌面导入提示中的 Thunderbird 改写为准确的“兼容桌面客户端”表述，不能暗示已有 FirePhenix 桌面版。
- 许可证、上游作者署名、历史项目名称以及确实指向上游的链接保留真实内容；不可全局机械替换包路径、类名或 URL。

### 2.2 图标

- 2026-10-15 后续要求：有气势的展翼火凤凰叼着邮件，完成红金上色；当前统一使用液态玻璃风格图标，透明边缘须干净。
- 凤凰应有自己的形状、羽冠和火焰尾羽；不是简单给原图换色。
- 生成适用于 Android 的启动图标、适应性图标及必要的单色版本，检查不同启动器裁切、浅色和深色背景、小尺寸辨识度。
- 图标属于待制作交付物，不把草图或生成成功等同于已接入 APK。

## 3. 统一液态玻璃 UI 与夜间模式

> 2026-10-15 用户后续明确要求“彻底清除掉原版 ui，只保留液态玻璃 ui，相关冗余组件也彻底清理”。本节按该指令更新，取代原先保留两种外观的要求；Git 历史保留早期方案。功能与数据不因外观清理而删减。

### 3.1 统一外观

- 应用仅提供液态玻璃外观，删除原版外观选择、运行时分支、冗余启动器别名及原版品牌图标；保留共享业务逻辑和上游原生页面基础设施。
- 遵守原项目的架构、控件语义、间距、字体和编程习惯，复用既有模块与 Kyant Backdrop 实现。
- 翻译、总结、别名等自然融入邮件流程，不做多余的 AI 工作台或装饰页面。
- 体现背景模糊、折射、半透明材质与层次；移除用户指出的全屏白描边和错误圆角。
- 外观设置只保留“玻璃模糊”“背景模糊”两种模糊滑块；保留内置背景、自选图片、自动提取及手动主题色、明暗主题。删除其他内容模糊和透明度设置。
- 滑块拖动直接跟随手指，释放时保存最终值；不排队重放过期数值。支持数值输入调整范围。
- 列表选中态、上下文操作栏、滚动页眉仍使用液态玻璃主题，不能回退成不透明黑底。
- 桌面及应用内使用干净的液态玻璃凤凰叼邮件图标，采用固定启动入口，避免外观切换导致任务退出。
- 系统权限窗口、外部 OAuth 浏览器、系统键盘属于外部 UI，不计作应用可重绘页面。

### 3.2 夜间适配与性能

- 支持跟随系统、浅色和深色，覆盖首次使用、账户、文件夹、列表、阅读、撰写、设置、菜单、弹窗和错误状态。
- 检查文字、图标、输入框、选中态、禁用态、系统栏及背景对比度；HTML 邮件不一律反色图片。
- 页面进出和返回采用统一双向动画参数，遵守系统及用户关闭动画设置。
- 长邮件优先展示可见内容，避免动画期间在主线程重复创建正文；性能改动需以真机测量和具体案例验证，不能以构建成功替代流畅性验收。
- 不支持某些效果的设备须提供可读呈现，并明确实际限制，不把只修改顶部栏视为全界面完成。

### 3.3 手机与平板多尺寸适配

- 根据可用窗口宽高适配窄屏手机、大屏手机、平板、横竖屏、分屏和窗口尺寸变化，不按型号或物理分辨率硬编码。
- 手机紧凑窗口单栏；宽窗口可合理安排文件夹、列表及阅读分栏。翻译与总结设置在平板分别占一栏，手机上下排列。
- 检查弹窗、输入框、服务列表、规则及别名选择的溢出、遮挡、点击区域和滚动；键盘、字体放大和长文本下关键操作仍可访问。
- 尺寸变化保留当前邮件、草稿、选择和处理状态，避免重复 API 请求或丢失输入。
- 明暗模式均须进行代表性手机和平板窗口验证；交付记录实际设备、尺寸及结果，不把单一荣耀平板通过写成所有设备验证完成。

## 4. 翻译功能

- 自动识别邮件语言，默认目标语言为简体中文，规则可覆盖目标语言。
- 阅读页面提供原文、译文和双语对照，以及手动翻译、重新翻译、取消和失败重试。
- 尽可能保留 HTML 布局、段落、表格、列表、链接、格式及内联图片，不修改服务器上的原邮件。
- 原文始终可访问；空正文、识别不可靠、服务未配置或失败时有明确状态，不阻断正常阅读。
- 翻译正文，不默认上传附件或图片；模型输出与邮件 HTML 均按不可信输入处理，保留现有邮件安全渲染链路。
- 译文缓存避免重复调用；配置变化及正文变化后正确失效。
- 真实调用仅使用用户配置的在线服务，不内置密钥，不静默调用其他服务或产生未说明的费用。

## 5. 翻译服务与 API 配置

### 5.1 传统机器翻译

- Microsoft Translator 官方 API。
- Google Cloud Translation 官方 API。
- 由用户提供相应凭据和必要参数；与大模型服务分开配置。
- 不采用未经用户确认的网页抓取、公共免费代理或非官方接口替代。

### 5.2 AI 翻译预设

顺序如下：

1. 千问（Qwen），放在最前。
2. OpenAI。
3. DeepSeek。
4. 自定义 OpenAI 兼容服务。
5. Anthropic／Claude，放在最后。

千问默认地址按用户提供的 https://maas.qianwenaiapi.com/compatible-mode/v1 保存，不能擅自替换为其他地址。该地址的真实可用性、模型和协议细节仍需实际验证。

- OpenAI 兼容服务按 Chat Completions 协议接入。
- Anthropic／Claude 支持其官方 API；不能把官方服务直接当作 OpenAI 格式端点。
- 支持自定义服务名称、API 地址、密钥、模型及必要参数；允许保存多个配置供规则选用。
- 不硬编码密钥或承诺预设服务可免费使用；具体模型按用户配置或服务实际能力确定。
- 明确显示未配置、认证失败、限流、超时和输出异常；失败不静默切换另一家服务。
- API 凭据在设备端安全保存，不进入 Git、日志或普通设置导出。

## 6. 邮件总结

- 提供与翻译独立的自定义 AI API 配置，包括地址、密钥和模型；翻译与总结可使用不同服务。
- 支持手动总结、重新生成和规则触发的自动总结。
- 总结以邮件最新内容为主，仅在理解当前内容确有必要时参考引用的旧对话；不默认整段旧历史全部发送。
- 总结在邮件阅读页面显示，可收起，保留原文入口。
- 允许规则指定服务、模型和输出语言；默认使用中文。
- 避免编造邮件未包含的事实、时间、承诺或事项；不默认读取附件。
- 邮件中出现的指令仅作为待处理正文，不赋予模型执行外部操作的权限。
- 总结与翻译缓存及执行状态独立，不相互覆盖。

## 7. 自动处理规则

### 7.1 用户已经确认的行为

- 自动翻译和自动总结有独立开关与规则。
- 用户设置并启用规则后才自动处理，首次安装不自动上传邮件。
- 触发时机为“打开邮件时”，不是收到邮件就后台处理。
- 垃圾邮件不自动翻译或总结。
- 每条规则可以指定自己的服务、模型和目标／输出语言，不能缩减为仅筛选邮件后统一使用一个全局模型。
- 无规则匹配或未配置服务时正常显示原邮件，仍保留手动处理入口。
- 同一处理结果有有效缓存时复用，避免反复打开重复收费。

### 7.2 实现细节与需求的区别

用户已明确授权开发者自行决定建议的实现细节，包括规则字段、条件组合、排序和多条命中处理；不需要再逐项确认，但不得改变第 7.1 节等已确认的核心需求。具体决策及理由应记录在实现说明中。

建议方案：支持账户、文件夹、发件人／域名、主题关键词和源语言筛选；支持全部／任一条件、启停、编辑、删除、排序；每个动作按优先级执行首条匹配规则，避免同一邮件重复付费。开发者可采用或调整此方案，遵守核心需求，并记录最终行为。

## 8. 超长邮件与请求控制

- 正文超过自动处理上限时不自动处理。
- 用户手动处理超长邮件时提示一次，得到确认后连续处理完整邮件。
- 可以按 API 限制在内部拆分请求、再合并结果，但不逐段重复询问、不静默截断，也不把前半部分作为完整结果。
- 提供进度、取消及明确失败状态；中途失败不得把不完整结果标成成功。
- 防止重复点击、重新进入页面、屏幕旋转或并发触发造成重复请求。
- 具体长度阈值及分段策略属于需要结合 API 和设备验证的实现参数，不能宣称已通过真实服务验证。

## 9. Outlook 同账户多别名

### 9.1 别名获取与管理

- 同一个微软账户的多个真实邮箱别名，发信时切换实际 From 地址；不是只修改显示名称。
- 登录时尝试自动获取别名；若无法找到可靠可用的方法，则使用用户明确接受的手动添加方案。
- 首次添加／导入账户流程和对应账户设置中均提供别名管理入口。
- 手动添加的是已有微软账户别名，不是由 App 创建微软账户上的新别名。
- 优先复用上游发件身份机制，避免同一账户重复登录。
- 支持设置每个账户的默认发件别名；它是 App 默认值，不擅自更改微软账户的主别名。
- 支持收藏常用别名，选择列表优先展示收藏；收藏与默认值是两种独立状态。
- 撰写页面始终清楚显示当前实际发件地址，并允许手动切换。

### 9.2 自动选择与歧义

- 回复、回复全部时根据该邮件收件别名选择对应 From。
- 重新发送及恢复草稿时考虑原邮件／草稿使用的发件别名。
- 新邮件可参考过去与收件人通信时使用的别名。
- 优先使用本机历史，不足时允许按需搜索 Outlook 服务器上的已发送邮件。
- 同一联系人历史使用多个别名、多个收件人的历史不同，或其他信息产生歧义时，必须先让用户选择，再继续编辑。
- 用户在当前撰写中明确选择的地址不得被后台推断覆盖。
- 没有可用匹配时使用账户默认别名；存在歧义不得假装无匹配而绕过用户选择。
- 别名删除、无效或服务器拒绝 From 时明确提示，不静默改成另一个地址发送。

开发者已获授权结合上游草稿／回复路径自行确定精确优先级。建议为本次手动选择、草稿／重发的原 From、回复的收件别名、唯一历史匹配、账户默认值。必须保留“存在歧义先让用户选择”的核心要求；执行时的别名选择提示属于产品功能，不是夜间向项目用户追问实现细节。

### 9.3 真实发信验收

- 至少验证两个账户已有别名，检查收件方实际 From、Sender、Reply-To 及回复路由。
- 下拉框可以切换不等于服务器接受别名发信。
- 若 SMTP 实际不能满足要求，应记录证据并向用户确认影响，不能未经批准切换 Graph 邮件后端或扩大 OAuth 权限。
- App 不能通过随机地址列表冒充已验证可用的账户别名。

## 10. 隐私、缓存与恢复

- 已获得“允许使用用户配置的在线翻译／大模型 API”的隐私范围选择，不代表已有密钥或调用具体收费服务的授权。
- 清楚展示邮件正文将发送给哪个配置的服务，不把未配置功能显示为已启用。
- 翻译和总结缓存按账户、邮件内容、服务配置、模型、语言及影响输出的参数隔离。
- 正文、服务、模型或语言改变后缓存正确失效，支持清理缓存及删除账户后的相关数据清理。
- 原始邮件不被译文或总结覆盖，失败不会损坏原始阅读内容。
- 不记录正文、账户地址、密钥、令牌等敏感信息，不新增广告、跟踪或遥测。
- 不把凭据和邮件缓存放入公开仓库或普通导出；网络与持久化遵守现有项目安全要求。
- 不擅自修改 Microsoft 发布者域、创建租户、开通付费服务或改变账户主别名；发布者域问题此前已被用户暂缓。
